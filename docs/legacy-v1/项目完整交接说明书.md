## 一、项目结论摘要

本项目已经从两个相互独立、依赖 Dify 的单机派单问答页面，升级为一套本地统一运行的“多人登录 + 权限管理 + 会话隔离 + Markdown 知识管理 + 可追溯混合检索”系统。

当前完成的能力：

1. 热线派单顾问页面，端口3786。
2. 派单小助手页面，端口3790。
3. 管理后台，端口3791。
4. 用户、部门、角色、权限和审计管理。
5. 多用户登录与会话、历史记录、案例数据隔离。
6. Markdown知识的上传、编辑、版本、审核、发布、停用、恢复和回滚。
7. MySQL保存业务事实，Qdrant与FTS5作为可重建索引。
8. 839份历史Markdown原件已正式纳入知识管理体系。
9. 备份、只读校验、隔离恢复演练、日志轮转和统一健康检查。

当前明确没有完成的能力：

1. 不是完整的12345工单流转系统。
2. 尚无派单、转派、退回、承办、办理意见、催办、超期、提醒、办结等业务流程。
3. 尚未实现PDF、Word、扫描件或OCR解析。
4. 尚未建设跨服务器部署、统一身份认证、短信、消息推送或移动端。

因此，当前准确定位是：**多人使用的热线派单智能辅助与知识管理系统**，而不是完整的12345业务受理办理平台。

## 二、项目起点与最初问题

项目起步时存在三个主要部分：

- “热线派单顾问”：阻塞式问答页面，原来直接调用 Dify。
- “派单小助手”：流式问答、历史会话和案例页面，原来依赖 Dify 会话及数据集接口。
- 本地知识检索：Python FastAPI + Qdrant + SQLite FTS5，供外部知识库协议调用。

最初系统的主要限制：

- 没有登录、用户、角色和权限体系。
- 会话和案例使用本地SQLite，不能可靠支持多人隔离。
- 知识只能通过目录和脚本维护，没有后台增删改查。
- 原始资料与切片后的知识源容易混淆。
- Qdrant中的向量点缺少统一的文档、版本、切片管理链路。
- 两个前端分别维护，运行入口和配置分散。
- 系统仍受Dify工作流、会话和知识数据集约束。

用户随后确认的长期方向是升级为多人使用的派单业务系统，并先完成用户体系与知识管理基础。完整的12345工单业务流程留给后续项目阶段。

## 三、最重要的数据概念

### 3.1 权威原件与派生知识源

项目中曾经存在两个容易混淆的目录：

- `knowledge-original`：839份拆分前的原始Markdown，是历史资料的权威原件归档。
- `knowledge-source`：10,384个经过清洗、拆分或派生的检索摄入文件，不是原件归档。

阶段0的旧索引基于 `knowledge-source`，共有39,147个Qdrant点和39,147条FTS记录。阶段7改为以839份原件为文档主体重新切片，生成20,916个可追溯切片。

数量从39,147下降到20,916的原因是取消了10,384个派生文件的文件边界和重复结构，并非知识原件丢失。旧索引完整保留，可随时回退。

### 3.2 现在的知识存储方式

- `data/kb-assets`：受控知识原件存储，采用SHA-256内容寻址。
- MySQL：保存文档、版本、正文、切片正文、文件元数据、审核记录和索引任务。
- Qdrant：只保存向量及检索载荷。
- SQLite FTS5：只保存关键词全文索引。
- MySQL不保存向量；Qdrant和FTS均可从MySQL与受控原件重建。

## 八、认证、权限和账号

### 8.1 认证机制

- 服务端Session，数据库只存令牌SHA-256摘要。
- `sid` Cookie为HttpOnly、SameSite=Lax；正式HTTPS环境应启用Secure。
- 密码使用bcrypt，无法从数据库反查。
- 改密、停用和登出会撤销相应会话。
- 非安全方法要求CSRF令牌和同源Origin。

### 8.2 四类默认角色

| 角色 | 主要职责 |
|---|---|
| `system_admin` | 用户、部门、角色权限、系统配置、审计和全部知识操作 |
| `kb_admin` | 查看、编辑、审核、发布知识，查看用户和部门 |
| `kb_reviewer` | 查看并审核知识 |
| `user` | 使用系统并查看知识 |

管理员及历史账号的初始口令只保存在本机被Git忽略的记录中，不应写入代码、Git或交接文档。接手人应在首次登录后修改密码。

## 九、知识管理标准流程

1. 知识管理员创建或选择分类、来源。
2. 上传Markdown，后端验证格式、大小、批量和文件名。
3. 系统保存内容寻址原件，并创建文档v1草稿。
4. 编辑正文时创建新版本，不覆盖旧版本。
5. 草稿提交审核。
6. 审核员通过或驳回；通过后生成切片和索引任务。
7. Worker把新切片暂存到索引，暂不影响当前发布版本。
8. 全部任务项成功后激活新版本并切换发布指针。
9. 失败时展示原因，可重试；旧版本继续检索。
10. 停用是软删除并删除派生索引，不删除原件和审计。
11. 恢复或回滚通过新的任务重新建立索引。

- 轮转只归档，不自动删除历史日志。
- 索引任务使用租约；Worker中断后过期租约可被接管。
- 成功任务项不会重复处理；失败任务需显式重试。
- 不得直接修改MySQL任务状态或Qdrant载荷伪造成功。

## 十五、已知限制与注意事项

1. 当前主要面向本机或可信内网，服务监听127.0.0.1。
2. 生产HTTPS部署时必须设置Secure Cookie并重新评估代理IP获取方式。
3. IP限流在反向代理部署前应增加可信代理配置，不能直接信任任意转发头。
4. 单文件上传上限2MiB，超大型Markdown需要另行制定流式解析策略。
5. 当前仅支持Markdown；PDF、DOCX和OCR不能通过改扩展名绕过。
6. 数据库与备份目前都在同一D盘，不能抵御整盘损坏，应增加异盘或离线备份。
7. 云模型可用性和速度仍取决于外部服务；本地检索正常不等于生成模型一定可用。
8. 历史 `migration/MIGRATION_STATUS.md` 同时记录早期去Dify阶段，其阶段编号与后来“多人化和知识管理”计划曾有重叠；以 `migration/PROJECT_REFACTOR_PLAN.md` 及本说明书为最终主线。
