交接目的：供新的 AI 或开发者从当前真实状态继续工作。接手者应先读本文，再读冻结需求文档与 docs/adr。冻结需求中的 PostgreSQL 选型已被 ADR-009 正式覆盖为 MySQL。

## 1. 项目背景和演变

本项目是“基于大语言模型与 RAG 的 12345 热线工单智能研判系统 V2”，目标是根据工单给出建议承办单位、政策与职责依据、历史案例、责任边界、风险提示，并保存人工反馈和完整引用证据。

V2 已脱离 Dify 主链路，也不在 V1 旧代码上继续重构。此前从 D:\热线派单系统 迁移了原始知识资料、整理后知识资料、历史案例资料及关键文档，新建独立工作区。

已确认的演变：

1. 新建独立 V2，不复制 V1 旧服务代码、虚拟环境、日志、备份和模型缓存。
2. Business API 采用 FastAPI、SQLAlchemy、Alembic。
3. 原 PostgreSQL 方案已正式切换为 MySQL；MySQL 是冻结的业务事实唯一真源。
4. Qdrant 是独立 RAG 检索层，不能代替业务数据库。
5. Service 只能通过 KnowledgeGateway 检索，不能直接依赖 Qdrant SDK。
6. 真实 Qdrant 通过独立 Knowledge API 接入，该服务负责 Embedding、混合检索和底层 Qdrant 操作。
7. LLM 目前只有 Gateway 契约和 Mock，尚未接入真实模型。

## 2. 当前冻结架构

```text
assistant-ui / Next.js
        ↓
FastAPI Business API
        ├─ Service → Repository → MySQL
        ├─ AnalysisService → KnowledgeGateway
        │                     ├─ MockKnowledgeGateway
        │                     └─ QdrantKnowledgeAdapter
        │                              ↓
        │                        Knowledge API → Qdrant
        └─ AnalysisService → LLMGateway → MockLLMGateway
```

不可破坏的边界：

- MySQL 是工单、研判、反馈和会话等业务事实的唯一真源。
- Qdrant 只保存知识和历史案例的检索投影。
- 前端、Router、Service 不得直接访问 Qdrant。
- Service 不得绑定 DeepSeek、OpenAI 等具体 SDK。
- 一条工单可有多条研判，重新研判不能覆盖历史结果。
- 引用必须保存当时内容快照。
- Dify 不得重新进入主链路。

## 5. MySQL 当前状态

当前 V2 数据库为 hotline_ai，字符集 utf8mb4，排序规则 utf8mb4_unicode_ci，驱动为 mysql+pymysql。连接来自 .env。当前业务数据为空，验证脚本产生的数据已经清理。

.env 含本机密码与 API Key，已经被 .gitignore 排除。不得打印、提交或复制其中的秘密。生产环境不得长期使用 root，应创建最小权限应用账户。

### 5.1 实际 10 张业务表

| 表 | 职责 |
|---|---|
| users | 用户、基础角色和所属部门 |
| departments | 标准部门主数据及上下级关系 |
| work_orders | 当前及历史工单的完整业务事实 |
| analysis_records | AI 每次独立研判、模型和输入快照 |
| answer_citations | 引用来源标识、内容快照、分数和 metadata |
| feedback | 人工采纳、否定、部门修正及说明 |
| conversations | 完整会话主记录 |
| messages | 会话中的用户和 AI 单条消息 |
| saved_cases | 工单或研判的收藏、典型案例标记 |
| knowledge_bases | 外部知识库注册和映射，不保存正文或向量 |

alembic_version 是迁移管理表，不是业务表。

### 5.2 主要关系

- work_orders 1:N analysis_records
- analysis_records 1:N answer_citations
- analysis_records 1:N feedback
- conversations 1:N messages
- saved_cases N:1 work_orders
- 推荐部门、实际部门和人工最终部门关联 departments

### 5.3 历史案例设计澄清

V2 没有独立 MySQL historical_cases 表，这是原冻结设计，不是误删：

- work_orders 保存真实历史工单和最终承办单位等事实，source_case_id 关联外部原工单。
- saved_cases 只标记其中值得复用的典型案例。
- Qdrant historical_cases 是语义检索副本，不是业务主表。
- answer_citations 是某次研判的引用快照，不是历史案例主数据。

当前 work_orders、saved_cases、answer_citations 均为 0 条，历史业务数据尚未导入 V2 MySQL。

### 5.4 Migration

当前只有 0001_initial_schema.py，通过冻结的 SQLAlchemy metadata 创建或删除全部 10 张表。真实 MySQL 已完成空库升级、回滚和再次升级。

技术债：后续 schema 变更必须新增显式增量 migration，不能继续用 create_all/drop_all 代替版本化变更。

## 6. RAG 与真实 Qdrant

### 6.1 Gateway 契约

位置：backend/gateways/contracts.py

KnowledgeGateway.search 的输入为 query、knowledge_base_ids、top_k、filters，输出为 RetrievalResult 列表。标准结果包含 evidence_id、knowledge_base_id、external_id、document_id、document_title、point_id、content、score、metadata。

业务层不得使用 Knowledge API 或 Qdrant 的原始返回结构。

### 6.2 Mock 与真实实现

backend/gateways/mocks.py 包含 MockKnowledgeGateway、MockLLMGateway、MockKnowledgePublisher。Mock 必须保留，用于稳定单元测试。

真实实现位于 backend/gateways/qdrant_adapter.py。QdrantKnowledgeAdapter 调用独立 Knowledge API 的 GET /health 和 POST /retrieval，不直接加载模型或调用 Qdrant SDK。

Adapter 已处理连接失败、超时、鉴权失败、404、空结果、缺失 metadata、非法 JSON 和异常结构。这些异常统一派生自 KnowledgeGatewayError；FastAPI 已注册 503 JSON 处理器，知识服务故障时不得静默裸答或伪造依据。

backend/gateways/factory.py 按环境变量切换：

```text
KNOWLEDGE_GATEWAY_MODE=qdrant  → QdrantKnowledgeAdapter
KNOWLEDGE_GATEWAY_MODE=mock    → MockKnowledgeGateway
```

真实参数全部来自 QDRANT_URL、QDRANT_API_KEY、QDRANT_COLLECTION、QDRANT_TIMEOUT。注意：QDRANT_URL 当前指向 8088 Knowledge API，不是 6333 裸 Qdrant。

### 6.3 交接时真实环境

- Knowledge API：http://127.0.0.1:8088，状态 ok
- Qdrant：http://127.0.0.1:6333，healthz 通过
- Collection：hotline_dispatch_v2
- Point：20,916
- 部门职责、权责清单、政策法规、历史案例四类检索均有真实结果

### 6.4 关键外部依赖风险

Knowledge API、Qdrant 可执行文件、Qdrant 数据、lexical 索引、离线模型和知识服务代码仍位于旧目录 D:\热线派单系统。V2 当前只实现调用端 Adapter。

在知识服务完成独立迁移或重新部署前，不得删除旧目录，否则 6333/8088 和真实检索会失效。旧目录目前作为独立外部知识服务部署位置，不是 Business API 主链路代码。

### 6.5 历史案例追溯缺口

真实历史案例能从 Qdrant 检索，但其 payload 没有稳定 work_order_id、source_case_id 或 case_id，因此目前无法从检索结果回查 V2 MySQL work_orders。

这属于数据同步和 metadata 缺口，不是增加 MySQL historical_cases 表的理由。后续导入历史工单并发布检索副本时，应写入稳定 work_order_id 或 source_case_id。

## 7. AI 研判流程

AnalysisService.analyze 当前流程：

```text
读取 WorkOrder
→ KnowledgeGateway.search
→ LLMGateway.analyze
→ 校验引用 evidence_id
→ 新增 analysis_records
→ 新增 answer_citations 快照
→ 提交事务
```

模型返回不存在的 evidence_id 时会报错，不保存伪造引用。真实 Qdrant 完整测试使用真实检索加 MockLLMGateway；真实 LLM 尚未接入，不能描述为真实 AI 模型已上线。
