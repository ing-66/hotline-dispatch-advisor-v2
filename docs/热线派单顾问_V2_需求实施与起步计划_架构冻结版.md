# 12345热线工单智能研判系统 V2

## 需求说明书 · 实施文档 · 起步计划（架构冻结版）

版本：V1.0 / 2026-09-07  
状态：开发基线 / 架构冻结候选

> 本文档的首要目标不是“写得完整”，而是避免项目再次出现颠覆性重修。任何实现都必须优先服从本文档中的架构边界、数据主权、依赖隔离和变更规则。

---

# 1. 项目重新定位

热线派单顾问 V2 不再作为 Dify 智能体的前端包装，而是一个独立的 12345 工单智能研判系统。

核心技术链路固定为：

```text
assistant-ui 前端
    ↓
自有业务后端 API
    ├── PostgreSQL 业务数据库
    ├── Knowledge API（外部知识库服务）
    │      ↓
    │    Qdrant
    └── LLM API（DeepSeek / 其他兼容模型）
```

系统解决的核心问题保持不变：

1. 快速识别工单诉求并给出建议承办单位；
2. 从部门职责、权责清单、法规政策、历史案例中检索依据；
3. 生成可追溯的研判结论、责任边界、历史案例和风险提示；
4. 记录人工反馈，使正确案例能够持续沉淀和复用；
5. 保证“有依据再判断”，避免模型编造政策或责任依据。

---

# 2. 架构冻结原则（不可随意改变）

## 2.1 五条一级原则

1. **Dify 不再进入主链路。** V2 不依赖 Dify Workflow、Dify Chatflow 或 Dify 数据结构。
2. **业务数据库与 RAG 知识库分离。** PostgreSQL 管业务事实；Qdrant 管可检索知识向量。
3. **PostgreSQL 是业务事实唯一真源。** 历史工单、最终承办单位、人工反馈等发生冲突时，以 PostgreSQL 为准。
4. **Qdrant 中的历史案例是检索副本，不是第二套业务数据库。** 它由真实历史工单加工、同步而来。
5. **业务后端不绑定 Qdrant 内部实现。** 研判模块只调用统一 KnowledgeGateway / Knowledge API；以后换向量库时不改业务逻辑。

## 2.2 二级原则

- assistant-ui 是可替换前端，不得承载业务规则。
- LLM 通过 LLMGateway 调用，不在业务代码中写死 DeepSeek。
- Prompt 必须版本化，LLM 输出必须通过固定 JSON Schema 校验；每次研判保存 input_snapshot_json。
- 一条工单允许产生多条 AI 研判记录，历史研判不得覆盖。
- 一次会话允许包含多条消息，会话与消息必须分表。
- AI 引用的知识证据必须保存“当时的内容快照”，避免知识库更新后无法追溯。
- 第一版不建设完整企业级 RBAC，不自建知识库文档/切片/索引后台，不把向量存进 PostgreSQL。
- 新功能默认通过扩展实现，不通过修改既有核心表语义实现。

### 关键隔离

- 前端不得直接调用 Qdrant。
- 前端不得直接调用 LLM。
- AnalysisService 不得直接 import 某个 Qdrant SDK。
- AnalysisService 不得直接依赖某个模型 SDK。
- KnowledgeGateway 和 LLMGateway 是稳定边界。

# 5. 数据模型与数据库设计

V2 核心数据库控制在 10 张左右，避免“为了范式而拆表”。

## 5.1 核心表

### 01 users — 用户

职责：保存基础登录用户和所属部门。

建议字段：

- id
- username
- password_hash
- display_name
- role（第一版仅 admin / user）
- department_id
- status
- created_at
- updated_at

### 02 departments — 部门

职责：统一部门主数据，供历史工单、AI 推荐、人工最终派单引用。

建议字段：

- id
- code
- name
- parent_id
- active
- metadata_json

### 03 work_orders — 工单

职责：保存“题目本身”和真实业务事实。

建议字段：

- id
- source_case_id（外部原工单 ID，可空）
- title
- content
- request_type
- address
- source
- event_time
- actual_department_id（历史真实承办单位 / 最终承办单位）
- status
- metadata_json
- created_at
- updated_at

**规则：AI 输出不得覆盖 work_orders 的原始诉求。**

### 04 analysis_records — AI 研判记录

职责：保存“AI 对工单做过的每一次答案”。

建议字段：

- id
- work_order_id
- conversation_id
- trigger_message_id
- model_provider
- model_name
- prompt_version
- primary_department_id
- recommended_departments_json
- conclusion
- responsibility_boundary
- confidence
- risk_warning
- evidence_summary
- input_snapshot_json（记录当次研判实际输入快照）
- raw_output_json
- created_by
- created_at

**关系：work_orders 1 : N analysis_records。** 重新研判时新增记录，不覆盖旧记录。

### 05 answer_citations — 研判引用

职责：记录 AI 当次研判引用了哪些知识证据，并保存快照。

建议字段：

- id
- analysis_id
- knowledge_base_id
- evidence_id / qdrant_point_id
- source_record_id（历史案例时可存 work_order_id）
- citation_type
- document_title
- content_snapshot
- source_url
- relevance_score
- metadata_json
- created_at

**content_snapshot 必须保留。** 即使知识库以后更新，也能解释当时为什么做出该判断。

### 06 feedback — 人工反馈

职责：保存人工对 AI 研判的采纳、否定和修正。

建议字段：

- id
- analysis_id
- user_id
- feedback_type
- adopted
- final_department_id
- comment
- created_at

### 07 conversations — 会话

职责：保存左侧历史记录中的“一整段会话”。

建议字段：

- id
- user_id
- title
- status
- created_at
- updated_at

### 08 messages — 对话消息

职责：保存会话里的每一句用户/AI消息。

建议字段：

- id
- conversation_id
- role
- content
- model_name
- analysis_id（若该 AI 消息对应研判结果）
- metadata_json
- created_at

**关系：conversations 1 : N messages。**

### 09 saved_cases — 收藏 / 典型案例

职责：从全部工单和研判记录中标记值得复用的典型案例。

建议字段：

- id
- work_order_id
- analysis_id
- user_id
- case_type
- note
- created_at

### 10 knowledge_bases — 外部知识库注册表

职责：只保存“系统有哪些外部知识库以及如何映射”，不保存知识正文和向量。

建议字段：

- id
- code
- name
- type
- remote_collection
- enabled
- config_ref
- description
- created_at
- updated_at

初始四类：

1. department_duties — 部门职责库
2. responsibilities — 权责清单库
3. regulations — 法规政策库
4. historical_cases — 历史案例库

### 可选 11 operation_logs — 操作日志

仅记录必要的系统操作和异常追踪。第一版不以“审计平台”为目标。

# 6. 历史案例：数据库与 RAG 的关系

这是本项目必须长期保持一致的核心规则。

```text
PostgreSQL / work_orders
        │
        │ 真实历史工单（唯一事实源）
        │
        ├── 业务查询 / 精确统计 / 最终承办单位
        │
        └── 经筛选、清洗、加工、同步
                     ↓
               Knowledge API
                     ↓
                  Qdrant
            historical_cases
                     │
             AI 语义相似检索
```

### 两者区别

**数据库历史工单**：强调真实、完整、结构化、可统计。  
**Qdrant 历史案例**：强调语义召回、案例匹配、给 AI 提供参考上下文。

### 同步规则

- Qdrant Point 必须携带稳定的 `work_order_id` / `source_case_id`。
- 只有满足入库条件的历史工单才进入 historical_cases。
- 历史工单更新后，知识库同步应采用 upsert，不新造重复案例。
- 删除或失效的业务记录必须能在知识库中标记失效或删除。
- 检索到历史案例后，若需要展示“最终承办单位”等精确信息，可按 work_order_id 回查 PostgreSQL 进行校验。

### 冲突处理

如果 PostgreSQL 与 Qdrant 的历史案例字段不一致：

> **PostgreSQL 永远优先。**

# 7. AI 答案到底参考什么

V2 采用“两路数据、不同职责”的原则。

## 7.1 RAG 知识库是 AI 研判的主要证据源

用于：

- 找部门职责
- 找权责事项
- 找法规条文
- 找语义相似历史案例
- 生成引用依据

## 7.2 业务数据库是精确事实工具

用于：

- 查某条真实工单完整字段
- 核验历史案例最终承办单位
- 精确统计数量、比例、时间范围
- 查询人工最终修正结果
- 查询已有研判、反馈和会话记录

## 7.3 禁止

- 不允许让 LLM 通过自然语言“猜数据库统计”。
- 不允许把 Qdrant 搜索结果当作业务唯一真相。
- 不允许在没有证据时生成伪法规、伪职责。

# 8. Knowledge API 需求契约

热线系统依赖的是 Knowledge API，而不是 Qdrant 数据结构。

## 8.1 最小接口

### GET /health

返回知识服务是否可用。

### GET /knowledge-bases

返回可检索知识库列表和状态。

### POST /search

请求示例逻辑：

```json
{
  "query": "公司拖欠工资三个月，应由哪个部门处理？",
  "knowledge_bases": ["department_duties", "responsibilities", "regulations", "historical_cases"],
  "top_k": 8,
  "filters": {}
}
```

返回每条 evidence 至少包含：

- evidence_id
- knowledge_base
- source_record_id（如 work_order_id）
- document_title
- content
- source_url（可空）
- score
- metadata

### 可选 POST /search/batch

一次向多个知识库并行查询，降低网络往返。

## 8.2 KnowledgeGateway

业务后端必须定义统一接口，例如：

```text
KnowledgeGateway.search(query, kb_codes, top_k, filters) -> Evidence[]
```

AnalysisService 只依赖 Evidence[]，不得依赖 Qdrant Point 原始结构。

## 8.3 历史案例发布接口

历史工单进入 RAG 不属于实时研判事务。发布通过独立 `KnowledgePublisher` 走 Knowledge API；若现有 Knowledge API 只有检索能力，则使用外部批处理同步，不改变热线业务主链路。

```text
KnowledgePublisher.upsert_case(work_order_id, case_payload)
KnowledgePublisher.delete_case(work_order_id)
```

# 9. LLM 研判流程

```text
当前工单
   ↓
保存/加载 work_order
   ↓
KnowledgeGateway 检索四类知识
   ↓
必要时按 source_record_id 回查 PostgreSQL 核验
   ↓
Evidence Pack（带 evidence_id）
   ↓
LLMGateway
   ↓
JSON Schema 校验
   ↓
analysis_records
   ├── answer_citations
   └── assistant message
```

## 9.1 固定输出字段

- 建议承办单位（第一建议 + 可选第二建议）
- 研判结论
- 政策/职责依据
- 历史案例
- 责任边界
- 协商参考（需要时）
- AI 置信度
- 风险提示

## 9.2 输出 Schema

模型必须返回结构化 JSON；UI 显示格式由前端决定。禁止让模型直接输出不可解析的整段富文本作为唯一结果。

## 9.3 引用规则

- 模型只能引用 Evidence Pack 中存在的 evidence_id。
- 后端校验引用 ID 是否真实存在。
- 任何“政策依据”“部门职责”若无合法 evidence_id，应标记“缺乏可核验证据”，不得伪造。

## 9.4 Prompt 版本化

每次分析必须记录 `prompt_version`。修改 Prompt 时新增版本，不覆盖旧版本，便于比较准确率和回归测试。

# 10. 前端需求（assistant-ui）

## 10.1 设计原则

- 保持 assistant-ui 的极简感。
- 不把后台管理功能塞进主聊天页。
- 不增加与研判无关的 Agent、插件、市场、工作流入口。
- 桌面端优先。

## 10.2 主界面

左侧：

- 新建研判
- 历史会话
- 收藏案例入口
- 设置（管理员/开发模式）

主区域：

- 用户输入工单
- AI 研判卡片
- 承办单位
- 研判结论
- 引用依据（可展开）
- 历史案例（可展开）
- 责任边界
- 风险提示
- 反馈按钮：采纳 / 不采纳 / 修正

## 10.3 交互要求

- 流式输出可以存在，但结构化结果必须最终落库后再标记“完成”。
- 知识库不可用时明确显示“知识检索失败”，不得静默退化成无依据回答。
- LLM 不可用时工单数据仍应保存。
- 重新研判必须生成新的 analysis_record。

# 15. 起步计划（第一轮必须按顺序执行）

## Step 0 — 冻结决策

开发前先创建以下 ADR：

- ADR-001：Dify 退出主链路
- ADR-002：PostgreSQL 与 Qdrant 分离
- ADR-003：PostgreSQL 为业务事实真源
- ADR-004：Knowledge API / Gateway 隔离 Qdrant
- ADR-005：LLMGateway 隔离模型供应商
- ADR-006：工单与研判分表
- ADR-007：会话与消息分表
- ADR-008：引用内容快照持久化

## Step 1 — 新仓库骨架

先创建目录、依赖、配置、健康检查和测试框架，不迁移旧代码。

## Step 2 — 只建数据库，不接 AI

先让以下流程成立：

```text
创建会话 → 写消息 → 创建工单 → 创建空研判记录 → 保存反馈
```

## Step 3 — 先接 Mock Knowledge API

用固定 Evidence 模拟知识检索，验证 AnalysisService 的输入输出结构。

## Step 4 — 再接真实 Knowledge API

只有 Mock 流程通过后才接真实 Qdrant 知识服务。

## Step 5 — 接 Mock LLM，再接真实 LLM

先用固定 JSON 模拟模型输出，通过 Schema 校验、落库、引用校验后，再接 DeepSeek/兼容模型。

## Step 6 — 最后接 assistant-ui

前端只消费稳定 API，避免“UI 做着做着反过来决定后端结构”。

# 16. 验收标准

## 16.1 功能验收

1. 用户可创建会话并提交工单。
2. 工单原始内容保存到 work_orders。
3. 系统可从四类知识库检索 Evidence。
4. AI 能输出结构化研判结果。
5. 所有依据必须可展开查看来源和内容快照。
6. 一条工单可重新研判且保留历史版本。
7. 用户可采纳、否定或修正承办单位。
8. 可收藏典型案例。
9. 历史会话可恢复。
10. Knowledge API 或 LLM 故障时系统有明确降级行为。

## 16.2 数据验收

- PostgreSQL 与 Qdrant 的历史案例通过稳定 ID 关联。
- answer_citations 可在知识库更新后继续解释历史答案。
- 任何 AI 生成字段不覆盖历史工单原始字段。
- 对话数据与业务工单可独立存在。

## 16.3 架构验收

使用代码搜索确认：

- frontend 不含 Qdrant SDK
- frontend 不含数据库连接
- AnalysisService 不含 Qdrant SDK
- AnalysisService 不直接调用具体模型 SDK
- 无 Dify 依赖
- Prompt 有版本号
- 数据库迁移可从空库完整执行

# 17. 必测场景

1. 同一工单连续研判三次，三条 analysis_records 全部保留。
2. 同一会话十轮对话，conversation 只有一条、messages 有多条。
3. Qdrant Knowledge API 超时：禁止无提示直接让模型裸答。
4. LLM 超时：工单和检索证据不丢失，可重新发起分析。
5. 检索到法规但模型引用不存在的 evidence_id：后端拒绝该引用。
6. 历史案例 Qdrant payload 与 PostgreSQL 最终承办单位不一致：展示以 PostgreSQL 校验值为准，并记录异常。
7. 知识库文档更新后，旧 answer_citations 仍可显示当时快照。
8. 切换 LLM 供应商后，不修改 AnalysisService。
9. Knowledge API 更换底层向量库后，不修改业务表和前端。
10. assistant-ui 被替换后，后端 API 和数据库无需重构。

# 18. 安全与配置

- 生产环境 API Key 不保存在浏览器 localStorage。
- LLM Key、Knowledge API Token 使用服务端环境变量或服务端加密配置。
- 日志不得输出完整 API Key。
- 用户输入、模型输出、引用证据分别保存，避免混写。
- 数据库所有写入走后端服务层。
- SQL 使用 ORM/参数化查询。
- 对知识库返回内容视为“不可信外部输入”，进入 Prompt 前做长度、类型和字段校验。

# 19. 防止再次颠覆性重修的制度

## 19.1 架构决策记录 ADR

任何涉及以下内容的修改，必须新增 ADR：

- 增删核心数据表
- 改变 PostgreSQL / Qdrant 主从关系
- 让前端直接访问外部基础设施
- 更换 Knowledge API 契约
- 更换 AI 输出 Schema
- 引入完整 RBAC
- 引入知识库管理后台
- 引入真实 12345 系统集成

## 19.2 “先扩展、后改核心”规则

优先：新增 Adapter、Service、字段、JSONB metadata。  
谨慎：修改核心主键、删除表、改变历史数据语义、让一个表承担两个领域职责。

## 19.3 数据主权表

| 数据 | 唯一真源 | 可有副本 | 冲突时 |
|---|---|---|---|
| 原始工单 | PostgreSQL | Qdrant 可有检索副本 | PostgreSQL |
| 最终承办单位 | PostgreSQL | Qdrant payload 可复制 | PostgreSQL |
| AI 研判结果 | PostgreSQL | 无需复制 | PostgreSQL |
| AI 引用快照 | PostgreSQL | 原知识在 Qdrant | answer_citations 快照 |
| 文档切片/向量 | Knowledge Service/Qdrant | 不进业务库 | Knowledge Service |
| 会话与消息 | PostgreSQL | 无 | PostgreSQL |
| Prompt 模板 | 代码/配置版本库 | analysis 记录版本号 | 版本库 |

## 19.4 变更前四问

每次准备加功能，先回答：

1. 这是热线研判业务能力，还是基础设施能力？
2. 现有 Service / Gateway 能否扩展完成？
3. 是否真的需要新表？能否用已有实体 + JSONB metadata？
4. 这项修改如果未来撤销，会不会污染核心业务数据？

只要第 4 问答案是“会”，就必须先做架构评审。

# 20. 多轮架构审视结果

## 审视 A：是否还会因为换知识库再次重做？

结论：只要严格保持 KnowledgeGateway，**不会**。Qdrant、Milvus、Weaviate 或其他知识服务的变化限制在 Adapter 层。

## 审视 B：数据库与知识库都有历史案例，会不会双重维护？

结论：不会。PostgreSQL 是原始事实源，Qdrant 是由它加工出的检索投影。稳定 work_order_id 串联两边。

## 审视 C：assistant-ui 以后不满意会不会又推倒？

结论：不会。UI 只调用 Business API；只要 API 契约不变，可以换前端。

## 审视 D：以后想加完整权限，会不会重建业务表？

结论：不应。当前 users.role 只满足第一版。未来引入 RBAC 时新增 roles / permissions 等授权表，不改 work_orders / analysis_records 的业务语义。

## 审视 E：以后模型更换或 Prompt 大改会不会污染历史结果？

结论：不会。analysis_records 保存 model_provider、model_name、prompt_version 和 raw_output_json，历史研判可比较、可追溯。

## 审视 F：知识库更新以后旧答案是否失去依据？

结论：answer_citations 保存 content_snapshot，旧答案仍可解释。

## 审视 G：当前 10 表是否可能再次膨胀成 20+ 表？

结论：允许未来增长，但必须由真实业务需求驱动。知识库内部表、索引任务表、企业级权限表不得因为“看起来专业”提前进入业务数据库。

## 审视 H：历史案例发布链路会不会绑死 Qdrant？

结论：不会。历史案例发布走 KnowledgePublisher / Knowledge API；如果现有知识服务只有检索 API，可用外部批处理完成发布，不改变研判主链路。

# 22. 给 Coding Agent 的首轮执行边界

首轮只完成“架构骨架”，不得主动扩展范围。

必须：

1. 创建 V2 新仓库；
2. 建立 frontend / backend / docs；
3. 建核心数据库 migration；
4. 建 Repository / Service / Gateway 接口；
5. 给 KnowledgeGateway、LLMGateway 写 Mock；
6. 建健康检查与自动化测试；
7. 完成 ADR-001 至 ADR-008；
8. 自测后提交 git diff 和验收结果。

禁止：

- 扫描或复制整个 V1 代码库后直接重构；
- 接 Dify；
- 自建 Qdrant 文档后台；
- 增加复杂角色权限；
- 增加未列出的可见页面；
- 为“未来可能用到”提前建表；
- 在 Mock 未通过前接真实 AI 和真实知识库；
- 在后端 API 未稳定前深度改 assistant-ui。

首轮完成的定义不是“能聊天”，而是：

> **核心边界正确、数据模型正确、依赖方向正确，并且后续每一个功能都可以在不推翻骨架的情况下逐步挂上去。**
