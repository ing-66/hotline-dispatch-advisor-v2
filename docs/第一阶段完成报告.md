## B. 实际数据库表

`users`、`departments`、`work_orders`、`analysis_records`、`answer_citations`、`feedback`、`conversations`、`messages`、`saved_cases`、`knowledge_bases`。

## C. 数据关系

- `work_orders` 1:N `analysis_records`
- `analysis_records` 1:N `answer_citations`
- `analysis_records` 1:N `feedback`
- `conversations` 1:N `messages`
- 部门、用户、工单、研判、反馈和收藏通过外键保持 N:1 关系

## D. Gateway

- `KnowledgeGateway.search(query, knowledge_base_ids, top_k, filters)`
- `LLMGateway.analyze(work_order, evidence, prompt_version)`
- `KnowledgePublisher.upsert_case(work_order_id, case_payload)` / `delete_case(work_order_id)`
- 三者均有 Mock，可在不修改 `AnalysisService` 的前提下替换实现。

## F. 与需求文档的偏差

- 原 PostgreSQL 基线已由后续 ADR 正式调整为 MySQL；数据库切换验证见 MySQL 切换报告。
- API 目前只实现健康检查、创建/读取工单和创建会话的最小入口，其余起步 API 将随业务闭环补齐。
- assistant-ui 当前使用本地 Mock Adapter，仅验证独立运行与边界，不连接真实 Business API。

## G. 技术债务

- 初始 Alembic revision 通过冻结模型元数据创建/删除表，后续 schema 变更必须改用显式增量 migration。
- 尚未建立持续运行的真实数据库 CI；单元测试仍使用 SQLite 隔离库。
- 尚未实现认证、完整 CRUD、错误状态和日志体系。

## H. 下一阶段建议

进入阶段 B，补齐工单、会话、消息、研判、反馈和收藏的 Business API 闭环；保持 Mock Gateway，不接真实 Qdrant 或 LLM。
